# Архитектурный контракт установщика

## Назначение

Репозиторий содержит независимый публичный статический сервис установки
Community Club. Сервис не является частью репозитория приложения и имеет
самостоятельный жизненный цикл.

## Публичные маршруты

- `GET /club` — выдача Bash-установщика с Content-Type `text/plain`.
- `GET /health` — endpoint проверки доступности; успешный ответ означает, что
  сервис может принимать запросы.

Маршрут `/club` не является страницей и не собирает входные данные по HTTP.
Он возвращает тело Bash-установщика как обычный текст.

## Фиксированный источник

Сервис использует только значения из `config/source.json`:

- `repository`:
  `https://github.com/yurec77nepran-hash/community-club-source.git`;
- `commit`: `1ac31045e815d5b12569b34cbeaf53b97a7e81d0`.

Эти значения являются серверной конфигурацией и не принимаются из query,
form-data, JSON body, headers или иных данных публичного вызывающего. Публичная
вызывающая сторона не может выбрать другой репозиторий или commit.

## Канонические параметры установки

Скачанный Bash-процесс получает ровно два канонических параметра через окружение
на целевом VPS:

- `DOMAIN` — домен, на котором будет доступно приложение;
- `ADMIN_EMAIL` — email администратора.

Имена переменных передаются в bootstrap приложения без переименования. Сервис
не принимает эти значения по HTTP и не извлекает их из запроса к `/club`.
Параметр `INSTALL_EMAIL` на этом этапе не поддерживается и не добавляется как
совместимость.

## Границы ответственности

### Публичный сервис

Сервис отдаёт Bash-текст по `/club` с Content-Type `text/plain` и предоставляет
endpoint `/health`. Он не выполняет установку и не собирает параметры через
HTTP.

### Host-side execution boundary

Скачанный Bash выполняется на целевом VPS и является единственной границей для
действий, требующих доступа к Docker, Git, DNS, файлам хоста или системным
правам. `DOMAIN` и `ADMIN_EMAIL` доступны этому процессу как переменные
окружения. Публичная вызывающая сторона не получает доступ к хосту и не исполняет
привилегированные команды.

### Итоговая последовательность

В итоговой реализации Bash-процесс на целевом VPS выполняет следующие действия
в пределах host-side boundary:

- запуск только от `root` и удержание lock в root-owned каталоге `/run/lock`;
- получение зафиксированного commit из GitHub в новый приватный staging через
  Git с очищенным окружением и проверка точного `HEAD`;
- замена исходного кода без выполнения Git-команд в старом target и без смены
  пути `/opt/community-club`, определяющего Compose project/volume identity;
- сохранение `.env`, `secrets/` и `garage.toml` как runtime-состояния;
- использование заранее настроенной DNS A-записи для `DOMAIN`;
- запуск штатного bootstrap с фиксированными `PATH`, `HOME`, locale и только
  `DOMAIN`/`ADMIN_EMAIL`, при этом lock удерживается до его завершения.

Контейнер сервиса установщика не получает доступ к целевому VPS, Docker socket
или файловой системе хоста. Он только публикует статический Bash-файл.

Все host-side действия вызываются из `main`, который является последним
оператором файла. Поэтому синтаксически целый, но усечённый до `main` поток не
начинает установку.

## Ограничения доступа

В контракте нет проверок лицензии, подписки, invite-кода или иных access
checks. Добавление таких ограничений требует отдельного изменения контракта.

## Размещение сервиса

Контейнер обслуживает только HTTP на внутреннем порту `8080`. `compose.yaml`
публикует его исключительно на loopback-интерфейсе
`127.0.0.1:${HTTP_PORT:-3980}` и не публикует HTTPS или UDP-порты. Публичный
HTTPS для `shablon-clud.nepran-yuri.ru` завершается в системном Caddy хоста,
который проксирует запросы на `127.0.0.1:3980`.

Production-копия установщика размещается в `/opt/community-club-installer`, а
host-конфигурация маршрута хранится в
`/etc/caddy/conf.d/community-club-installer.caddy`. Контейнер не использует
ACME, не хранит сертификаты и не требует volumes. Порты `80/443` остаются в
исключительном владении host Caddy.
